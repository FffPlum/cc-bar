# GitHub Release 更新说明

每次发布都在此目录新增一份与 tag 同名的文件，例如发布 `v1.0.40` 时创建 `release-notes/v1.0.40.md`。该文件和版本号一起提交；GitHub Actions 会校验它存在且非空，然后把**全文原样**放在 Release 正文开头。

Release 标题不做定制，沿用 GitHub 默认的 tag 名（如 `v1.0.40`）。

这不是按时间持续追加的 `CHANGELOG.md`。每份文件只描述一个版本，方便发布前审阅、发布后追溯和重跑 CI。

[highlights.md](highlights.md) 的近期新功能会追加在 Release 正文末尾，见下文「近期新功能」。

应用内更新窗口显示的内容与 Release 正文一致。发布工作流用本版说明和 `highlights.md` 生成 `release-notes.md`，并与 ZIP 更新包和 `appcast.xml` 一起签名上传。HTML 注释不会出现在应用内日志；源文件及 GitHub Release 正文仍保持原样。生成的文件不提交到此目录，也不用维护第二份日志。

## 读者和场景

主要读者是在应用内更新窗口里决定要不要升级的用户。窗口只显示最新一版的说明和近期新功能，跳过几个版本的用户看不到中间各版。所以每一版都要让人先从亮点了解主要变化，再从分类条目找到和自己有关的细节。

应用内窗口按行渲染 `## ` 标题、`- ` 列表、普通段落和行内 Markdown，不显示图片，空行会被忽略。为兼顾 GitHub Release 和应用内窗口，标题和条目各占一行，不使用表格、图片或嵌套列表。

## 文件格式

参考 [CodexBar v0.82.0](https://github.com/steipete/CodexBar/releases/tag/v0.82.0)，先写本版亮点，再按新增、改进、修复列出具体变化。以下只是格式示例，发布时以实际改动为准：

```markdown
## 本版亮点

- 可以在应用内查看更新内容并安装新版本
- 服务顺序可在设置中调整，并同步到各展示位置

## 新增

- 在「检查更新…」里查看更新内容，下载后自动安装并重启；从旧版升级到本版需手动安装一次

## 改进

- 在「设置 → 服务与账号」拖动服务可调整顺序，菜单栏、悬浮窗和统计页同步

## 修复

- Codex：修复子代理用量导致统计页出现没有标题的对话
```

**亮点**

- 放在最前面，用 1～3 条概括最重要的用户可感知变化，让读者快速判断与自己是否有关。
- 同一项变化可以在后面的分类中补充入口、细节或注意事项，但不要原样重复亮点。

**条目**

- 每条一件事，表达简洁，结尾不加句号；分类内按对用户的影响从大到小排列。
- 需要用户操作、升级后默认值或行为会变、已有数据会被迁移的，写进相关条目或放在第一条，写清变成了什么、想改回去在哪里改。
- 新功能和位置变化写出入口，用界面上的原名，如「设置 → 服务与账号」「检查更新…」。
- 只涉及某个服务或功能的，在条目开头点明名称，如「Codex：……」；修复写清用户遇到的现象。
- 空分类省略；不强制列出 PR 链接和贡献者，仅在信息真实且对用户有帮助时提及。

**特殊情况**

- 只有一处改动时，可以只保留「本版亮点」和一条说明。
- 没有用户可感知的改动时，只写：`本版为内部维护更新，功能与上一版一致。` 不要虚构稳定性、性能或功能收益。

**不使用**：版本标题、图片、emoji、徽章、下载表格、安装说明等每版重复的固定段落。

## 近期新功能

`highlights.md` 写最近一个月里值得用户知道的新功能，读者是从 Release 页下载、或不常更新的用户，帮他们发现自己可能还没用过的功能。发布时它追加在本版说明后面，中间多空一行；Release 正文和应用内更新内容都是这个顺序。

每次发版写完本版说明后，顺带检查并更新这个文件：

- 第一行固定为 `最近一个月新增的功能，你可能还没用过：`，下面是条目，不写版本号和日期。
- 只写最近约一个月内、特别重要的新功能：用户不知道就用不上、或明显改变使用方式的。修复、后台改进（耗电、性能）、小众或影响面窄的改动不写。
- 每条写清用户能做什么和入口，用界面原名，40 字以内，结尾不加句号。
- 最多 10 条，按重要程度排列。不够就少写，不凑数；没有合适的内容时清空文件，工作流会跳过这一段。
- 本版说明里已经写了的功能不重复写，下次发版再考虑放进来。
- 超过一个月的条目删掉。

## 撰写流程

1. **盘点**：读上一个 `v*` tag 到当前 HEAD 的提交正文，必要时看 diff，重点看界面文案（`tr("…")`）和文档的改动。逐项记下：改了什么、用户在哪里看到、改之前怎样、改之后怎样、对应哪个提交。这一步只是草稿，不写进文件。
2. **取舍**：去掉用户感知不到的改动——重构、测试、文档、CI、构建脚本、文案微调，以及说不出"用户看到了什么不同"的布局调整。同一件事的多个提交合并成一条。
3. **排序**：找出本版最主要的变化写入亮点，再按新增、改进、修复分类，分类内按影响排序。
4. **写作**：名称以界面上显示的中文为准（`tr()` 第二个参数），不用代码里的类名、字段名和内部概念。
5. **自检**：每一句都过下面的问题，有一项不通过就重写或删掉。

## 自检问题

- 不看代码的用户能看懂吗？有没有缓存、快照、前缀、口径、归属、Provider 这类内部说法（界面上本来就这么叫的除外）？
- 用户知道在哪里用到、怎么触发吗？
- 写的是用户得到的结果，还是开发做了什么工作？
- 能对应到具体的提交吗？有没有夸大或没做的事？
- 删掉这条，用户会少知道什么吗？不会就删。
- 亮点能让用户快速了解本版最重要的变化吗？分类细节是否提供了额外信息？

## 改写对照

以下是过去版本里的写法和改写后的写法：

| 原写法 | 问题 | 改写 |
|---|---|---|
| Codex 模型渠道前缀丢失，影响提供商归属 | 内部说法，用户看不懂 | 修复在 Codex 中经 Command Code 等渠道调用的模型，用量记到了错误的提供商下 |
| 统计页对比区间与自定义日期联动不正确 | 读起来像在报告一个现存问题 | 修复选了自定义日期后，统计页的对比区间没有跟着变化 |
| 额度周期在补记缓存时可能归错账号或被误判为不完整 | 写了实现过程 | 修复额度页的历史周期偶尔记到错误的 Codex 账号下 |
| 主窗口标题栏、长名称与 Codex 副账号套餐的显示 | 只说改了哪里，没说变成什么样 | 说不出用户能看到的变化，删掉 |
| 精简设置页、统计页和引导页的文案，凭据说明与实际行为一致 | 用户感知不到 | 删掉 |
| 概览新增用量构成与高消耗对话，单日图展示近 30 天 | 一条里并列几件无关的事 | 拆成两条，分别写清入口和效果 |
| 悬浮窗支持右键菜单 | 没说菜单里有什么 | 悬浮窗右键可隐藏悬浮窗或打开设置 |

## 示例

改动较多的版本：

```markdown
## 本版亮点

- 「服务与账号」集中管理服务，刷新失败时可直接查看原因

## 改进

- 在「设置 → 服务与账号」的同一行开关服务，并选择是否显示在菜单栏和悬浮窗
- 刷新失败时，点该行行尾按钮可查看失败原因
- 其他 Codex 账号移到 Codex 下方，重置次数和删除在 ⋯ 菜单里
```

带有行为变化的版本：

```markdown
## 本版亮点

- 统计排行可以按 Tokens 或费用排序

## 改进

- 统计排行默认按 Tokens 排序，可在「设置 → 外观与显示 → 统计 → 排行口径」改回按费用
- 隐私模式改为默认关闭，自动检查更新改为默认开启；之前手动设置过的保持不变
- 悬浮窗右键可隐藏悬浮窗或打开设置

## 修复

- 修复选了自定义日期后，统计页的对比区间没有跟着变化
```

只有一处改动的版本：

```markdown
## 本版亮点

- 「设置 → 服务与账号」中的「更多 Codex 账号」默认折叠，标题显示已导入的账号数
```
